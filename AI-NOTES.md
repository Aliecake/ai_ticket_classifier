# AI Notes

## Structured Outputs

### Problem

LLMs naturally generate free-form text, while application code usually needs
predictable typed data.

### Mental model

Structured Outputs are similar to deserializing an API response into a typed DTO.
The difference is that an LLM generates the values.

### Pattern used in this project

1. Define a Pydantic model.
2. Use enums for fields with a controlled vocabulary.
3. Pass the model to `client.responses.parse(...)`.
4. Receive `response.output_parsed`.
5. Let Pydantic validate field types and constraints.
6. Use the resulting object in ordinary Python code.

### Why not just say "return JSON"?

A prompt can request JSON, but that is still a best-effort instruction.
Structured Outputs constrain the response to the supplied schema and the SDK
parses it into the specified Pydantic type.

### Important limitation

Schema compliance does not mean factual correctness.

A response can be perfectly valid JSON and still contain a bad classification.
That is why this project will later add labeled examples and evaluation.

### Design decisions

- `category`, `priority`, and `route` use enums to prevent arbitrary labels.
- `confidence` is constrained to values from `0.0` through `1.0`.
- `summary` is length-limited.
- Empty ticket input is rejected before making an API request.
- Unit tests validate the schema without calling the model.

### Questions to revisit

- How should ambiguous or multi-topic tickets be represented?
- Should confidence be generated by the model or calculated another way?
- When should a ticket support multiple categories?
- How should refusals and incomplete responses be handled?
- Which schema changes would break previously stored results?
